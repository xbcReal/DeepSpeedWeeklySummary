📌 本周一句话总结

本周是「大特性收尾 + 静默正确性问题清扫」的一周：v0.19.4 补丁版本发布（8/6，约 41 个 PR、7 位新贡献者）； 非托管梯度累积（managed_gradient_accumulation=false）在三天内从 ZeRO-2 一路铺到 ZeRO-3 与 CPU/NVMe offload，面向 RL / Tinker 协议后端的能力基本闭环； DeepNVMe 的 host pinning 被拆成独立 pin_memory op，从此不再依赖 libaio； MoE/AutoEP 侧拿到 Ampere/Ada 的 Triton grouped-GEMM；同时合入了 4 个会静默算错结果的严重 bug 修复。

#8180 Add Triton grouped-GEMM for MoE experts on Ampere/Ada Feature Perf
Author: hwchen2017 | Merged: 2026-08-03 | +1076/-10 (10 files)
本周最有分量的性能特性。AutoEP 的专家计算走 torch._grouped_mm，而它只在 Hopper (sm90+) 上有融合 kernel；在 Ampere/Ada（A100/A6000/A40/RTX 30xx，sm80/86）上会静默退化成逐专家的 Python 循环（_grouped_mm_fallback），每个专家一次 at::mm 外加一次 offs 的 device→host 同步。新增 deepspeed/moe/group_gemm_triton.py：一个 autograd-aware 的 Triton grouped GEMM，可直接替换 torch._grouped_mm（2D×3D + offs），在 sm<9.0 上自动启用（sm90+ 仍走 native），并支持 fp16/bf16/fp32 的前反向；tile→group 映射在 device 侧算出，彻底消除 device→host 同步；trans_b 让专家权重以原生 [E,N,K] 布局传入、靠 stride 转置，反向直接产出原生布局的权重梯度，省掉一次 contiguous 拷贝。可用 DS_DISABLE_TRITON_GROUPED_MM=1 关闭。
实测（dim=2048, hidden=768, bf16, 不均衡分布）：32 experts / 1848 tokens 下 forward 0.213ms vs Torch 0.755ms vs for-loop 1.603ms；前反向 0.622ms vs 2.222ms vs 22.732ms，最高约 3.5×（对 Torch）/ 36×（对 for-loop）。
#8203 Unmanaged gradient accumulation: ZeRO stage 2 support Feature
Author: sfc-gh-truwase (Olatunji Ruwase) | Merged: 2026-08-05 | 承接 #8184
把上周落地的「非托管梯度累积」（managed_gradient_accumulation=false）扩展到 ZeRO stage 2。与 stage 0/1（backward 只本地累积、step 才 reduce）不同，stage 2 必须每次 backward 都 reduce/partition 才能保住显存特性——这与非托管模式并不冲突，因为 reduce-scatter 是线性的：把 N 次调用方控制的 backward 的已 reduce 分片累加，等价于在边界处 reduce 一次。micro-step 计数保持关闭，边界仍由调用方掌控，只把 averaged_gradients 的收尾推迟到 step()（新增 finalize_gradient_accumulation_boundary()）。 额外收益：stage 2 现在支持 overlap_comm（异步 reduce 被限制在 per-backward 路径内，收尾前同步），stage 0/1 仍拒绝。验证：2-GPU 全量 -k Unmanaged 22 passed。
#8217 Unmanaged gradient accumulation: ZeRO stage 3 support Feature
Author: sfc-gh-truwase | Merged: 2026-08-05 | 叠加在 #8203 之上
继续推到 ZeRO stage 3（非 offload）。stage 3 与托管模式一致，每次 backward() 都把梯度分区进 __param_id_to_grad_partition；step() 只负责通过 finalize_gradient_accumulation_boundary() 标记边界。由于 stage 3 解禁，原先藏在 stage-3 守卫后面不可达的 ZeRO 参数 offload 转为显式拒绝。验证：-k Unmanaged 29 passed，ZeRO-3 核心回归 158 passed / 62 skipped。
#8225 Unmanaged gradient accumulation: ZeRO offload support Feature
Author: sfc-gh-truwase | Merged: 2026-08-09 | +369/-98 (11 files) | 承接 #8217
系列收尾：扩展到 ZeRO 优化器状态与参数 offload（CPU/NVMe）。stage 2/3 仍每次 backward 做 reduce/partition，step() 收尾被推迟的 offload 边界工作（梯度范数 + FP32/NVMe 拷贝）；stage 1 继续在 step() 通过 allreduce_gradients() reduce。至此非托管梯度累积覆盖 ZeRO 0/1/2/3 + offload 全栈，仅流水线并行、DeepCompile、Apex AMP 与 stage-0/1 的 overlap_comm 仍不支持。验证：-k Unmanaged 31 passed（含 test_unmanaged_matches_managed_optimizer_offload[1|2|3] 与 stage-3 参数 offload）。
#8236 Split native host pinning into standalone pin_memory op Feature Refactor
Author: sfc-gh-truwase | Merged: 2026-08-09 | +537/-70 (33 files)

#8212 Share DeepNVMe pinned-tensor manager and route swap buffers through I/O handles Feature Perf
Author: sfc-gh-truwase | Merged: 2026-08-05 | +162/-44 (15 files)
DeepNVMe 只在 buffer 是 torch-pinned 或被该 handle 的 pinned-tensor manager 管理时才跳过 bounce buffer 拷贝。但这个 manager 此前是「每 handle 一个」且只认精确基址，导致一个 handle 分配的 buffer、或共享池的 narrow/view 从另一个读写 handle 提交时都认不出来，永远走 bounce。此 PR 把它改成进程级共享单例 + 基于地址区间的识别（C++ 侧 deepspeed_pin_tensor_t 变 shared() 单例并加 std::mutex，is_managed 支持 range 判定），并让 swap 子系统统一通过 I/O handle 获取 pinned 内存、查询 pinned 状态（新增 handle.is_pinned(buffer)）。是 #8236 / #8211 这条 pinning 重构线的第一步。
#8186 Wiring up offload_opt_states Feature
Author: pengdurice | Merged: 2026-08-03 | +593/-151 (6 files)
让 DeepCompile 的优化器状态 offload 在 inductor 下真正可用、并可从 config 打开。要点：用 dc 命名空间下的 4 个注册 op 取代闭包（图里只带 tensor anchor + 整数索引，活跃 tensor 留在 module state）；用 ORDERED effect 注册让原生 inductor 既保留这些 op 又保住顺序（reload-before-sync 是正确性关键）；容量优先调度 [(0,[z3]), (1,[for_init, z3, move_opt_states])]——profiling 前先把状态清到 host，使计划基于内存下限制定；修掉三处静默的 stream 竞争（拷贝等优化器写入、record_stream 防 reload buffer 被提前复用、拷贝流写 reload buffer 前等计算流——缺了这条会在 backward 中途覆盖活跃激活，表现为 NaN loss）。
实测（Qwen3-14B, 8×H200, ZeRO-3, fp32 状态 22.2GB/rank）：eager ZeRO-3 与 ZeRO-Offload 在 seq 2400 均 OOM，DeepCompile 无 offload 会在 recompile 处挂掉，带 offload 才跑得起来。

#8207 fix(zero3): async grad offload + pinned offload buffers by default Perf Bugfix
Author: delock | Merged: 2026-08-07 | +187/-46 (17 files) | 含默认值变更
ZeRO-3 在 partition_grads() 里的梯度 GPU→CPU offload 用的是阻塞式 copy_()，目的 buffer 又默认是可分页 host 内存，于是这条拷贝被钉在同步、低带宽的 staged pageable 路径上，完全无法与 backward 计算重叠——尽管它本就跑在专用的 reduce_and_partition_stream 上。而 ZeRO stage 1/2 早已用 non_blocking=True，stage 3 是唯一的异类。改动：offload_config.py 把 offload_optimizer/offload_param 的 pin_memory 默认改为 True（异步全带宽 DMA 必需；只在 ulimit -l 很紧的机器上才需关掉）；stage3.py 改为 non_blocking=True；顺手删掉一个引用未初始化属性、且无调用者的孤儿 helper。
实测（4× RTX 4080-SUPER, autotp=2, offload_optimizer + cpu_adam）：Qwen2.5-1.5B backward 1810ms → 1308ms（-28%），Qwen2.5-3B 3097ms → 2540ms（-18%），显存与 FWD/STEP 不变。

#8158 Fix ZeRO-3 all_reduce param fetch stride for padded parameters Bugfix 静默数据损坏
Author: ebarkhordar | Merged: 2026-08-05
本周最值得警惕的静默损坏。Init._all_gather_coalesced 中启用 stage3_use_all_reduce_for_fetch_params 的分支，用对齐后的元素数（ds_numel_aligned）申请扁平 buffer，却用未对齐的 ds_numel 前进偏移。二者只在 ds_numel % world_size == 0 时相等，一旦参数有 padding，后续每个参数的基址就会落进前一个参数对齐跨度内 padding_i 个槽位。这些重叠槽位是前驱的分区 padding——而 _partition_param 用 torch.empty 分配分区，且在分区超出参数末尾的那个 rank 上只拷贝 elems_to_copy 个元素，尾部从未被写入、装的是分配器残留值。由于 fetch 是 SUM 语义的 all_reduce，这段未初始化尾部会被加进下一个参数的头部元素。兄弟 all_gather 路径写入同样 padding 但每个参数只 narrow 自己的 ds_numel，所以读不到——此损坏专属于 SUM 重建路径。
#8157 Fix DeepCompile ZeRO-3 gathered parameter ownership Bugfix
Author: tohtana (Masahiro Tanaka) | Merged: 2026-08-03 | +846/-23 (6 files)
DeepCompile 把 ZeRO-3 的 all-gather / release 插入编译图，但 Dynamo 因 graph break 跳过某个 frame 时，该 frame 会 eager 执行、不跑这些图操作（#8059 的 eager fallback 负责这种情况）。问题有四：(1) Dynamo guard 求值发生在外层 forward 上下文内、且 is_compiling() 为假，会被误判成真实 eager 执行而触发不必要的 all-gather；(2) fallback gather 的参数正常在 backward 后分区，但 backward 被跳过时这个清理不会跑；(3) 残留的 full 参数可能一直占着显存进入下一次 forward；(4) 被 GatheredParameters 上下文覆盖的参数必须保持 full 直到上下文退出，否则 fallback 清理会在使用中把它分区掉。此 PR 逐一区分处理：guard 求值时跳过 all-gather、下次最外层 forward 前分区残留的非持久 full 参数、并把 GatheredParameters 覆盖的参数移出 fallback 清理范围。
#8198 Fix AutoEP ZeRO-1/2 universal conversion Bugfix
Author: tohtana | Merged: 2026-08-07 | +533/-80 (9 files) | Fixes #8147
AutoEP 在 ZeRO stage 1/2 下保存的 checkpoint，专家优化器状态存成 ZeRO 分片 fragment，但 Universal Checkpoint 转换会先走通用路径去 merge 这些专家 fragment。当源 EP size > 1 时，转换可能把不同 EP rank 的数据混在一起并在 reshape 时失败；fallback 路径还可能产出缺少 repartition 元数据的专家 tensor，并在需要 FP32 master 的地方用了混精度模型权重。修法：在通用 merge 之前先从 checkpoint 元数据识别融合的 AutoEP 专家参数，按 EP-rank 顺序从 ZeRO fragment 重建 FP32 master 与 Adam 状态；用保存的 topology 设置同时兼容 expert-before-data 与 data-before-expert 两种 rank 布局；给每个专家状态都写入专家元数据以支持换 EP size 加载；并把流水线层发现限制到完整的 pipeline checkpoint 文件名，避免 per-expert 文件被误分类。
#8210 Fix ZeRO++ secondary shard copy for small params Bugfix
Author: ZyEng-Art | Merged: 2026-08-07 | Fixes #6659（2024 年的老 issue）
修复 ZeRO++ _partition_param_sec() 中「小参数与其二级分片不重叠」的边界情况。报告场景：shape [32] 的参数被 DP 对齐到 2048，zero_hpz_partition_size=16 下二级分片大小变成 128，于是对某些二级组 rank，secondary_start 已经超过 param.ds_numel、sec_numel 变成 0——而旧代码仍执行 one_dim_param.narrow(0, secondary_start, 0)，PyTorch 在起始索引越界时即使长度为 0 也会抛 IndexError。修法：sec_numel == 0 时跳过二级拷贝，并先把二级分片 buffer 清零，使未覆盖的 padding 保持确定性、不会把未初始化值泄漏进后续的 coalesced 量化。附带两个针对性回归测试。
#8216 Do not let one op builder's compatibility probe break importing deepspeed Bugfix
Author: adityasingh2400 | Merged: 2026-08-07 | Fixes #7452
import deepspeed 时 git_version_info.py 会探测每一个 op 的编译兼容性，无论调用方是否会用到，而且没人捕获探测失败。于是在「有可见 GPU 但没装 CUDA toolkit」的机器上，CUDA op builder 的 is_compatible() 抛出 MissingCUDAException，导致连纯 sharding 场景都无法 import deepspeed，ds_report 同样挂掉。新增 probe_is_compatible：探测失败即报告为不兼容并打印原因，用在 import 期扫描与 ds_report 两处。同时让 installed_cuda_version 在 nvcc 跑不起来时抛 MissingCUDAException——CUDA_HOME 经常指向 runtime-only 安装（bin 下没有 nvcc），原先那个裸 FileNotFoundError 会绕过 builder.py 里已有的两个降级到 CPU-only 的 handler。新增 3 个测试。
#8178 Make PipelineModule.set_checkpoint_interval actually change the interval Bugfix 静默无效
Author: vineethsaivs | Merged: 2026-08-04
set_checkpoint_interval() 赋值给 self.checkpoint_interval，但全仓库所有读者用的都是 self.activation_checkpoint_interval（forward() 依它分支和步进、_precompute_checkpointable_values() 用它做缓存键、PipelineEngine 直接赋它）。self.checkpoint_interval 在仓库里没有任何读取点，所以这个调用等于写了个死属性，激活重计算的调度静默保持原样。而且仅改成正确属性还不够——它喂给的 _precompute_checkpointable_values() 缓存失效逻辑本身也是坏的，此 PR 一并修掉。
#8199 Stop trim_mean sorting the caller's list in place Bugfix 静默数据错乱
Author: vineethsaivs | Merged: 2026-08-05
CommsLogger.comms_dict 按消息大小存并行列表 [count, latencies, algbws, busbws]，索引 i 表示第 i 次记录的 op。get_operation_summary() / log_all() 把这些列表交给 trim_mean，而后者原地 data.sort()——于是「只读」的汇总调用会把三个列表各自独立排序，彻底破坏它们之间的行对应关系。作者给出实测：latency [3.0,1.0,2.0] 汇总后变 [1.0,2.0,3.0]，而 algbw 排成另一种顺序，本该恒定的 latency[i]*algbw[i] 变成 [0.0055,0.0164,0.0492]，get_raw_data() 就把这份错乱数据交给下游。判定为非预期行为的证据：get_operation_summary() 已经写了 .copy() 并注释「创建快照以避免并发修改」——意图明确，只是那是浅拷贝。
#8208 Fix MLU_Accelerator conformance to the DeepSpeedAccelerator ABC Bugfix
Author: ebarkhordar | Merged: 2026-08-04

#8205 Preserve tensor learning rates in OneCycle Bugfix
Author: tohtana | Merged: 2026-08-03 | Follow-up #8202

#8230 [RFC] Universal checkpoint：非语义化的 per-parameter 几何分片映射 RFC / 架构提案
Reporter: delock | Created: 2026-08-07 | 状态: OPEN（Draft，2 条评论）
本周最有战略意义的设计提案，直接产自对 #8185（非均匀分片）与 #8168（ZeRO-3 checkpoint 合并）的 review。

问题：Universal Checkpoint 的转换/恢复 schema 目前是语义化的——靠 uc_info 里一组正则分类（TP_REPLICATED_PARAMETER_PATTERNS、PARAMETER_WITH_ROW_PARALLELISM_PATTERNS、VOCABULARY_PARAMETER_PATTERNS、PARAMETER_WITH_SUB_PARAMS、AUTOTP_UNSUPPORTED_PARAMETER_PATTERNS）按参数名判断它的架构角色。这把它锁在一个封闭的布局集合里：集合外的布局即使模型运行时能正常切分和训练，转换器也会标成 unsupported 并拒绝。提案点名了目前转不了的布局（BLOOM/CodeGen 交错式融合 QKV、Yuan 非连续共享 QK），并指出那个「盲目 torch.cat(dim=0)」的 fallback 是静默损坏的隐患。

提案：改成非语义的、per-parameter 几何分片映射——每个参数记录自己的 TP 分片与完整逻辑张量之间的几何对应关系；转换器与恢复器只执行这张映射，不再分类参数角色。这样任何模型能切的布局都能转换，转换器也不再与具体模型绑定。

作者补充的延伸价值：该 schema 还能解锁跨拓扑的在线权重传输。今天在两个并行度不同的实例之间搬权重（如在线蒸馏里 teacher tp=4 ↔ student tp=2，或训练中途调整 TP/DP），必须走一次磁盘往返：save → ds_to_universal 转换 → load。
#8231 Cleanup：移除 tp_shard 的进程级标量全局变量（num_kv_heads / tp_grain_size 等），改为显式传递 技术债 / Tracking
Reporter: delock | Created: 2026-08-07 | 状态: OPEN（2 条评论，jinyouzhi 表示强烈认同）
同样出自 #8185 的 review，单独立 tracking issue 以免遗失。tp_shard.py 把 num_kv_heads、tp_grain_size、num_attention_heads、n_embd 存成进程级可变全局变量（AutoTP 替换时 set_* 写入，get_shard_size / get_shard_size_list 读回）。因为是进程级的，同一进程里加载第二个 AutoTP 模型会覆盖它们，于是第一个模型后续的切分/gather 会静默读到错误值——这使得「一个进程跑多个 AutoTP 模型」根本不安全：teacher/student 不同 TP size、在线蒸馏，以及任何在第一个模型之后再建第二个 AutoTP 模型的流程（包括经 init_inference）都受影响。#8185 用 _freeze_partition_sizes 只治了一个症状（构造时解析一次、运行时不再读全局），但全局变量仍是新模型污染旧模型状态的通道。方向：把这份状态挪到 per-model，在 AutoTP.__init__ 里从模型算一次并显式穿过各 sharding helper，彻底删掉全局变量与 set_*/get_*。
