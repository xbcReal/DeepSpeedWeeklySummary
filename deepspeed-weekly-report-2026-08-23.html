#8293 Enable DeepSpeed support on Apple Silicon (MPS) with ZeRO Stage 1-3 Feature Platform
Author: PKUWZP (Zhipeng Wang) | Merged: 2026-08-23 | +352/-34 (13 files)
本周最重量级的平台扩展。Apple Silicon 支持第一阶段（phase 0）：让 M 系列 Mac 上单机训练用纯 PyTorch op 端到端跑通。MPSAccelerator 从占位实现升级为真实实现——接入 torch.mps 内存统计、fp16/bf16 支持（bf16 gated 到 macOS 14+）、torch.mps.Event、gloo 通信后端，并把 is_synchronized_device() 设为 True（MPS 后端目前只暴露单条 in-order 执行流，没有 CUDA 风格的 stream API 与 record_stream）。由于统一内存模型下 pin_memory 无意义（且 torch 会 raise），MPS 上 pin_memory 直接被做成 no-op；gloo 无法直接对 MPS tensor 做集合通信，deepspeed/comm/torch.py 相应打补丁。Metal kernels 将在 phase 1（#8300）落地并挂进新增的 op_builder/mps。ZeRO stage 1/2/3 现在都能在 M 系列 Mac 上完成 deepspeed.initialize + 一步训练。
#8283 Register native pinned host memory with CUDA for GPU DMA Perf Feature
Author: sfc-gh-truwase (Olatunji Ruwase) | Merged: 2026-08-23 | +369/-3 (6 files)
承接上周 #8236 把 pin_memory 抽独立 op 的工作。posix_memalign + mlock 得到的内存对 CPU 是锁定的，但 GPU 的 DMA 引擎并不把 mlock 页当作 pinned——所以之前 DeepNVMe 的原生 pin 内存做 H2D 时会被 torch 判为「非 pinned」而走 staged 拷贝。此 PR 在 pin_memory 分配后可选调用 cudaHostRegister（释放前 cudaHostUnregister），通过 accelerator hook 挂到 CUDA/其它后端，使 copy_(..., non_blocking=True) 能够真正 DMA。默认开启（DS_PIN_MEMORY_REGISTER_DEVICE=1），注册失败一次日志后回落到 mlock-only。H200 实测（4 MiB / 64 MiB / 256 MiB）：torch pinned 约 53 GB/s H2D，native-unregistered 约 10–17 GB/s，native-registered 恢复到 53 GB/s——与 torch pinned 完全对齐，是 mlock-only 的 3–5×。
#8282 Non-reentrant activation checkpoint CPU offload Feature Perf

#8215 Keep parameter dtype through ZeRO-3 weight quantization Bugfix 静默数据损坏
Author: adityasingh2400 (Aditya Singh) | Merged: 2026-08-19 | +68/-14 (2 files) | Fixes #7775
本周最典型的静默损坏。quantizer op（csrc/quantization/pt_binding.cpp）只支持 fp16——quantize_kernel 把 input_vals.data_ptr() 一律强转 __half*，dequantize 也绑定为 dequantize<__half>；CUDAQuantizer 直接透传，结果 bf16 + zero_quantized_weights 下 ZeRO-3 把 bf16 位当 fp16 位量化再恢复回 param.data 变成 fp16——训练在 dtype mismatch 处失败（issue 里的 BERT 就是这么挂的）。更糟的是量化前的位重解释：值早就错了，只是 dtype mismatch 掩盖了这一层。修法：CUDAQuantizer.quantize 入口先转 fp16 保证值读对，dequantize 加可选 dtype——每个 caller 请求自己参数的原始 dtype；ZeRO-3 gather 路径的 5 个 call site 都传参数 dtype；omit 该参数即保持原 fp16 返回，其它 caller 行为不变。
#8261 Fix int32 overflow in Triton grouped-GEMM expert offset Bugfix
Author: PKUWZP | Merged: 2026-08-17 | +37/-1 (2 files)
上周合入的 Triton grouped-GEMM（#8180）里 group_gemm_triton.py 把专家 base pointer 算成 selected * stride_be，用 int32 乘——stride_be = K*N 元素数，任何 2**31 / (K*N) 以上的专家索引直接 wrap 成负数，kernel 越界访问抛 illegal memory access。触发条件：64 个专家、K=4096, N=14336 时最后一个专家已在 3.70e9 元素位置（int32 上限 2.15e9）。prefer_triton_grouped_mm() 在所有 sm<90 设备与「torch._grouped_mm 不可用」的场景默认走 Triton，因此 fine-grained MoE + Mixtral 级 FFN 维度是真实触发路径。修法：expert index cast 到 int64 后再乘。是硬 fault 而非静默 corrupt，此前产出的数值无需怀疑。
#8270 Fix ZeRO-3 crash in AutoTP universal-checkpoint metadata Bugfix
Author: PKUWZP | Merged: 2026-08-19 | +61/-7 (2 files)
DeepSpeed-Chat 主用例被彻底堵住。DeepSpeedHybridEngine + ZeRO-3 直接在 deepspeed.initialize() 报 IndexError: tuple index out of range：_mark_uc_metadata()（#7908 引入的 AutoTP universal checkpoint 支持）无条件从 LinearLayer.__init__ / LinearAllreduce.__init__ 跑起来，读 param.shape[1] 重建 pre-TP 形状——但 ZeRO-3 下参数分片后本地是空一维 tensor，该索引越界。修法：加对 ZeRO-3 partition 的条件保护，只在真的能读到形状时才写 UC metadata。没这个修复 ZeRO-3 + HybridEngine 无法初始化——RLHF actor 的标准配置。
#8246 Fix repeated FlopsProfiler metric accumulation Bugfix 静默数值放大
Author: baremetaldevx86 (Vedant Chauhan) | Merged: 2026-08-23 | +35/-4 (2 files)
FlopsProfiler cleanup 忘了恢复 F.scaled_dot_product_attention 与 Tensor.__matmul__，导致 wrapper跨 session 累积：同一模型多次 profile 后 FLOPs / MACs 会持续变大。更糟的是 torch.bmm 的恢复代码写错：torch.bmm = old_functions[torch.matmul.__str__]——因为 torch.matmul 已先恢复，这一句把 torch.bmm 永久重绑到 torch.matmul，profiling 之后 torch.bmm 开始接受 broadcasting matmul 输入（对 bmm 无效）。修法：每个 patched op 用自己对应的 saved original 恢复；新增 CPU 回归测试专门覆盖重复 profiling + op 恢复。
